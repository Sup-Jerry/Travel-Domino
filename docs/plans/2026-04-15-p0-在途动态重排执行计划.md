# P0 在途动态重排执行计划（从“提示风险”到“给动作”）

- 日期：2026-04-15
- 计划级别：P0
- 适用项目：Travel Domino（HarmonyOS / ArkTS）

## 1. 目标与成功标准

### 1.1 目标
把当前“发现风险并提示”升级为“给出可执行动作并可一键落地”，让产品从规划器进化为旅行调度器。

### 1.2 成功标准
- 用户在执行态遇到天气/拥堵/延误时，系统能给出至少两套可执行方案（A/B）。
- 每个方案都能解释代价：保住了什么、牺牲了什么、预计影响时长。
- 用户可一键应用方案，失败可解释，且可回滚。
- 不新增数据库结构，不破坏既有软重排主链路。

### 1.3 非目标
- 本期不做 OTA/支付/供应链能力。
- 本期不做多人协作治理体系。
- 本期不新增复杂社交能力。

## 3. 分阶段执行计划（8个工作日）

### 阶段 1（D1）：统一在途风险触发口径
- 统一天气触发与执行态触发的软重排入口语义。
- 规范 `reasonCode` 与 `startFromEventId` 生成规则。
- 对齐日志与 UI 的语义，避免“同类问题不同说法”。

验收：同类风险在日志和 UI 上输出一致，且可追踪。

### 阶段 2（D2-D3）：风险前置提示（从“迟到”到“会崩哪里”）
- 在预览阶段输出影响面：后续影响节点数、预计偏移分钟数。
- 强化提示语义：从结果描述升级为后果描述。

验收：提示文本可直接回答“如果不处理，会影响哪些点”。

### 阶段 3（D4-D5）：A/B 方案生成与约束
- A 方案：保核心点位（可跳过/替代高风险点）。
- B 方案：保整体流畅（换序/缩停留）。
- 复用现有 `actionType`、`actionPayload`，不新增持久化字段。

验收：同一风险至少可给出 2 个可执行选项。

### 阶段 4（D6）：代价解释落地
- 为每个方案生成“收益/代价/预计影响分钟数/是否可回滚”。
- 在伴游说明与重规划预览弹窗统一展示。

验收：用户应用前即可看清 trade-off。

### 阶段 5（D7）：一键执行与失败回滚可见化
- 统一 `requestSoftReplan` 成功/失败/回滚反馈文案。
- 保持现有 immutable 校验与超时回滚机制。

验收：失败路径可解释、回滚状态可感知。

### 阶段 6（D8）：测试与门禁
- 补齐主链路与文案映射相关单测。
- 先跑客户端快速门禁，再跑全门禁。

验收：无新增失败，核心回归通过。

## 4. A-F 副作用扫描

### A. 直接影响范围
- 执行态天气建议与软重排应用链路。
- 伴游动作确认与 toast 反馈。
- AI 重规划预览中的方案表达。

### B. 间接影响范围
- 时间线重算触发点。
- 状态机软重排门禁。
- `computed_time / dynamic_* / day_offset` 展示一致性。

### C. 潜在副作用清单
- 数据：误命中可调整节点集合。
- 逻辑：锁定节点保护绕过风险。
- UI：方案说明与实际执行不一致。
- 性能：高频触发导致重复重算。
- 可维护性：reasonCode 膨胀且含义漂移。

### D. 高风险边界场景
- 进行中节点 + 锁定节点并存。
- 候选节点为空。
- 跨天偏移与顺序联动。
- 执行超时后的快照回滚一致性。

### E. 回归测试优先级
1. `requestSoftReplan` 主链路（最高）
2. 预览与代价解释一致性
3. 伴游按钮动作与文案映射

### F. 风险缓解建议
- 仅在 `READY / IN_PROGRESS / PAUSED` 生效。
- 严格沿用 immutable 校验与 timeout rollback。
- 日志统一前缀与关键字段，便于快速定位。
